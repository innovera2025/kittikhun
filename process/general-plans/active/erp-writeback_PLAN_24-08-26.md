# แผน: ส่งผลการนับกลับเข้า ERP (write-back)

**สถานะ:** ร่างแผน — ยังไม่เริ่มทำ รอการตัดสินใจของเจ้าของโปรเจค
**วันที่:** 24 สิงหาคม 2569
**ผู้ร้องขอ:** เจ้าของโปรเจค

---

## 0. สิ่งที่ต้องรู้ก่อนอ่านแผนนี้

งานนี้ **กลับด้านหลักการที่ระบบทั้งระบบสร้างมา** ไม่ใช่การเพิ่มฟีเจอร์ธรรมดา

ปัจจุบัน "ERP อ่านอย่างเดียว" ถูกบังคับไว้ 5 ชั้น ทุกชั้นต้องถูกแก้หรือปลด

| ชั้น | ที่อยู่ | สิ่งที่ต้องทำ |
|---|---|---|
| 1 · สิทธิ์ DB | login `tcl_reader` เป็น `db_datareader` | ต้องขอสิทธิ์เขียนเพิ่ม (ดู §5) |
| 2 · boot probe | `mssql.driver.ts` — พิสูจน์ตอนบูตว่าเขียนไม่ได้ **ถ้าเขียนได้จะปฏิเสธการ start** | ต้องเขียนใหม่ทั้งหมด ไม่ใช่แค่ปิด |
| 3 · statement guard | `assertReadOnlySql()` — บังคับให้ทุกคำสั่งขึ้นต้นด้วย `SELECT`/`WITH` | ต้องมีเส้นทางเขียนที่แยกออกมาและมี guard ของตัวเอง |
| 4 · interface | `ErpAdapter` + type `WriteishMethodName` ทำให้ **คอมไพล์ไม่ผ่าน** ถ้ามีใครเพิ่ม method ชื่อแนวเขียน | ต้องแก้ type guard |
| 5 · connection | `readOnlyIntent: true` | ต้องแยก pool สำหรับเขียน |

นอกจากนี้ยังขัดกับเอกสารที่เขียนไว้ชัดว่า **"การเขียนกลับ ERP ถูกตัดออกจาก scope ถาวร — ห้ามเสนอใหม่"** (`erp-adapter.ts` · `docs/erp-integration.md` §6)

**ข้อเสนอ:** ก่อนเริ่มเฟส 1 ขอให้ยืนยันเป็นลายลักษณ์อักษรว่ากฎเหล็กข้อนี้ถูกยกเลิกแล้ว เพราะเมื่อปลดชั้นป้องกันเหล่านี้ ความผิดพลาดของโค้ดจะไปถึงข้อมูลจริงของ ERP โดยไม่มีอะไรกั้น

## 1. เป้าหมาย

ส่งจำนวนที่พนักงานนับได้จากระบบนี้ กลับเข้าไปในระบบ ERP (`db_TCL`)

**ต้องตอบให้ชัดก่อนออกแบบ** — คำตอบเปลี่ยนรูปงานทั้งหมด

| คำถาม | ทำไมสำคัญ |
|---|---|
| ส่งกลับเพื่อ **บันทึกผลนับ** หรือเพื่อ **ปรับยอดสต็อกจริง** | ผลนับ = เขียนลงโมดูลนับของ ERP · ปรับยอด = สร้างเอกสารเคลื่อนไหวที่กระทบยอดคงเหลือและอาจกระทบบัญชี |
| ให้ ERP เป็นคนเปิดรอบนับ แล้วเรา mirror มา หรือเราเปิดรอบเองแล้วสร้างรอบใหม่ใน ERP | ตัวหลังต้องยุ่งกับการออกเลขเอกสารของ ERP ซึ่งเสี่ยงสูงมาก |
| ส่งเมื่อไร — ทันทีที่พนักงานกด หรือหลัง admin ปิดรอบและตัดสินข้อขัดแย้งครบ | กระทบเรื่อง idempotency และการย้อนกลับ |
| ต้องผ่านการอนุมัติในฝั่ง ERP ก่อนมีผลไหม | ถ้าใช่ เราเขียนเป็นร่างและปล่อยให้คนอนุมัติใน ERP = ปลอดภัยขึ้นมาก |

## 2. สิ่งที่รู้แล้วเกี่ยวกับฝั่ง ERP

จากการสำรวจ `db_TCL` จริง (`docs/erp-tcl-findings.md`)

**โมดูลนับสต็อกของ ERP มีอยู่แล้วและใช้งานจริง**

| ตาราง | บทบาท | คอลัมน์ที่เกี่ยวข้อง |
|---|---|---|
| `tbl_CountHdr` | หัวรอบนับ | `VoucherNo` `CountDate` `Emp_ID` `CountNo` `CountYear` |
| `tbl_CountDtl` | รายการในรอบ | `ItemCode` `Warehouse` `MainUnits` · `MainQty` = ยอดระบบ · **`CountQty` = จำนวนที่นับได้** · **`DifQty` = ส่วนต่าง** |

**นี่คือข่าวดีที่สุดของงานนี้** — ERP มีช่องรับผลนับอยู่แล้ว (`CountQty` / `DifQty`) ไม่ต้องประดิษฐ์โครงสร้างใหม่ และ `ItemCode` ตรงกับ item master 100% (96/96)

รอบนับที่มีอยู่จริงใน ERP: `CNT-2608-0001` (186 รายการ) · `CNT-2608-0002` (0) · `CNT-2608-0003` (96)

**สิ่งที่ยังไม่รู้และต้องถามฝ่าย ERP**

1. `VoucherNo` / `CountNo` / `CountYear` ออกเลขอย่างไร — มี sequence หรือ stored procedure หรือคนกรอกเอง
2. มีคอลัมน์สถานะ/อนุมัติใน `tbl_CountHdr` ไหม และค่าไหนแปลว่า "รอตรวจ"
3. เขียน `CountQty` แล้ว ERP คำนวณ `DifQty` ให้เอง หรือเราต้องเขียนเอง
4. มี trigger บนสองตารางนี้ไหม
5. หลังบันทึกผลนับ ERP ปรับยอดสต็อกด้วยขั้นตอนอะไร ใครกด
6. มี stored procedure ที่ตั้งใจให้ระบบภายนอกเรียกไหม (ทางที่ปลอดภัยที่สุด)

## 3. ทางเลือกสถาปัตยกรรม

### ทางเลือก A — ส่งออกไฟล์ให้ ERP นำเข้าเอง ⭐ แนะนำเป็นเฟสแรก

ระบบสร้างไฟล์ (CSV/Excel) ตามรูปแบบที่ฝ่าย ERP กำหนด แล้วเจ้าหน้าที่นำเข้าผ่านหน้าจอ ERP

- **ข้อดี:** ไม่แตะฐานข้อมูล ERP เลย · กฎเหล็กทั้ง 5 ชั้นอยู่ครบ · มีคนตรวจก่อนข้อมูลเข้า · ย้อนกลับได้ด้วยการไม่นำเข้า · ทำเสร็จได้ในเวลาสั้น
- **ข้อเสีย:** มีขั้นตอนที่คนต้องทำ ไม่อัตโนมัติเต็มที่
- **เงื่อนไข:** ERP ต้องมีหน้าจอนำเข้าผลนับ — ต้องถามก่อน

### ทางเลือก B — เรียก stored procedure ที่ฝ่าย ERP เขียนให้

ฝ่าย ERP เขียน SP เช่น `usp_ImportCountResult` แล้วให้สิทธิ์ `EXECUTE` เฉพาะตัวนั้น

- **ข้อดี:** อัตโนมัติเต็มที่ · ตรรกะการออกเลขเอกสาร ตรวจสอบ และ trigger เป็นความรับผิดชอบของ ERP · เราได้สิทธิ์แค่ `EXECUTE` ตัวเดียว ไม่ใช่ `INSERT`/`UPDATE` ทั้งฐาน · ขอบเขตความเสียหายแคบที่สุดในบรรดาทางที่เขียนจริง
- **ข้อเสีย:** ต้องพึ่งฝ่าย ERP เขียนให้ ควบคุมเวลาเองไม่ได้
- **หมายเหตุ:** `assertReadOnlySql()` ปิดกั้น `EXEC` อยู่ ต้องเปิดช่องทางแยกที่อนุญาตเฉพาะชื่อ SP ที่ whitelist ไว้

### ทางเลือก C — เขียน INSERT/UPDATE ลงตาราง ERP ตรง ๆ

- **ข้อดี:** ไม่ต้องรอใคร
- **ข้อเสีย:** เสี่ยงที่สุด — เราต้องเลียนแบบตรรกะภายในของ ERP เอง (การออกเลขเอกสาร สถานะ การคำนวณส่วนต่าง trigger การผูกบัญชี) ถ้าเลียนแบบไม่ครบ ข้อมูลใน ERP จะเสียแบบที่ฝ่ายบัญชีอาจไม่รู้ตัวเป็นเดือน และการย้อนกลับต้องทำด้วยมือทีละแถว
- **ความเห็น:** ไม่แนะนำ ยกเว้นฝ่าย ERP ยืนยันเป็นลายลักษณ์อักษรว่าเขียนตรงได้และให้สเปกครบ

**ข้อเสนอ:** ทำ **A ก่อน** เพื่อให้ใช้งานได้เร็วและไม่มีความเสี่ยง แล้วผลักดัน **B** เป็นเป้าหมายระยะกลาง · หลีกเลี่ยง C

## 4. ขอบเขตงานแยกตามเฟส

### เฟส 0 — ยืนยันและสำรวจ (ไม่แตะโค้ด)

1. เจ้าของโปรเจคยืนยันยกเลิกกฎ "ERP อ่านอย่างเดียว" เป็นลายลักษณ์อักษร
2. ตอบคำถาม 4 ข้อใน §1
3. ประชุมกับฝ่าย ERP ตอบคำถาม 6 ข้อใน §2
4. ขอสำเนาฐานข้อมูลสำหรับทดสอบ — **ห้ามพัฒนางานเขียนบนฐานข้อมูลจริงเด็ดขาด**

**เกณฑ์ผ่าน:** ตอบครบทุกข้อ และมีฐานทดสอบให้ใช้

### เฟส 1 — ส่งออกไฟล์ (ทางเลือก A)

| งาน | รายละเอียด |
|---|---|
| กำหนดรูปแบบไฟล์ | ตกลงกับฝ่าย ERP — คาดว่าเป็น `VoucherNo` `ItemCode` `Warehouse` `CountQty` `MainUnits` |
| endpoint ส่งออก | `GET /count/:id/export/erp` — admin เท่านั้น · ทำได้เฉพาะรอบที่ปิดแล้วและตัดสินข้อขัดแย้งครบ |
| กฎ `null ≠ 0` | รายการที่ **ไม่ได้นับ** ต้องไม่ถูกส่งออกเป็น 0 — ต้องตัดออกหรือมีคอลัมน์บอกสถานะ ตามที่ฝ่าย ERP กำหนด |
| บันทึกการส่งออก | ตาราง `erp_export_log` — ใคร ส่งเมื่อไร รอบไหน กี่รายการ checksum |
| ปุ่มบนจอ admin | ดาวน์โหลดไฟล์ + แสดงประวัติการส่งออก |

**เกณฑ์ผ่าน:** ฝ่าย ERP นำไฟล์เข้าได้สำเร็จบนฐานทดสอบ และยอดใน ERP ตรงกับรายงานของเรา

### เฟส 2 — เขียนกลับอัตโนมัติ (ทางเลือก B)

| งาน | รายละเอียด |
|---|---|
| ปลดชั้นป้องกันอย่างมีระเบียบ | แยก `ErpWriter` ออกจาก `ErpAdapter` — adapter อ่านยังคง read-only 100% · writer เป็นคนละ interface คนละ pool คนละ login |
| guard ของฝั่งเขียน | อนุญาตเฉพาะ `EXEC <ชื่อ SP ที่ whitelist>` เท่านั้น · ปฏิเสธ `INSERT`/`UPDATE`/`DELETE` ดิบทุกรูปแบบ |
| แก้ boot probe | ปัจจุบันปฏิเสธการ start ถ้าเขียนได้ · ต้องเปลี่ยนเป็น "ตรวจว่า login อ่านมีสิทธิ์อ่านอย่างเดียวจริง **และ** login เขียนมีสิทธิ์เฉพาะ SP ที่กำหนด" |
| แก้ type guard | `WriteishMethodName` ต้องยังบังคับกับ `ErpAdapter` เหมือนเดิม แต่ยกเว้น `ErpWriter` |
| ทำให้ส่งซ้ำได้โดยไม่ซ้ำ | ส่งเลขรอบของเราไปเป็น idempotency key · ต้องมี unique constraint ฝั่ง ERP ไม่งั้นความปลอดภัยอยู่ที่ความหวังอย่างเดียว |
| คิวและการลองใหม่ | ส่งไม่สำเร็จต้องเข้าคิว ไม่ใช่หายเงียบ — ใช้รูปแบบเดียวกับ outbox ของมือถือ |
| จอติดตาม | admin เห็นว่ารอบไหนส่งแล้ว/ล้มเหลว/รอส่ง พร้อมเหตุผล |

**เกณฑ์ผ่าน:** ทดสอบบนฐานสำเนา 3 กรณี — ส่งปกติ · ส่งซ้ำแล้วไม่ซ้ำ · ส่งกลางคันแล้วเน็ตหลุด

### เฟส 3 — เปิดใช้จริง

1. เริ่มจากรอบนับเดียว คลังเดียว โดยมีคนฝั่ง ERP เฝ้าดู
2. เทียบยอดใน ERP กับรายงานของเราทีละรายการ
3. เก็บ snapshot ของ `tbl_CountDtl` ก่อนเขียนทุกครั้ง ในช่วง 30 วันแรก
4. ผ่านแล้วค่อยขยาย

## 5. เรื่องสิทธิ์ฐานข้อมูล

**ห้ามให้สิทธิ์เขียนกับ `tcl_reader`** — บัญชีที่ใช้อ่านต้องยังเป็น `db_datareader` ล้วน เพื่อให้ชั้นที่ 1 ของกฎเหล็กยังทำงานกับเส้นทางอ่านทั้งหมด

ต้องสร้าง login ใหม่แยกต่างหาก เช่น `tcl_writer` โดย

- ทางเลือก B: ให้เฉพาะ `GRANT EXECUTE ON <SP>` ไม่ให้สิทธิ์ตารางใด ๆ เลย
- ทางเลือก C (ถ้าจำเป็นจริง): ให้เฉพาะ `INSERT`/`UPDATE` บน `tbl_CountHdr` และ `tbl_CountDtl` เท่านั้น ห้ามให้ `db_datawriter` เพราะนั่นคือสิทธิ์เขียนทั้งฐาน

รหัสผ่านของสองบัญชีต้องคนละตัว และเก็บคนละตัวแปรในไฟล์ตั้งค่า

## 6. ความเสี่ยงและการรับมือ

| ความเสี่ยง | ผลกระทบ | การรับมือ |
|---|---|---|
| เขียนผิดรอบ / ผิดคลัง | ยอดสต็อกใน ERP ผิด กระทบการขายและการผลิต | ตรวจสอบว่ารอบและคลังตรงกันก่อนเขียนเสมอ · เฟส 3 มีคนเฝ้า |
| ส่งซ้ำจนข้อมูลซ้ำ | ยอดถูกบันทึกสองครั้ง | idempotency key + unique constraint ฝั่ง ERP |
| `null` กลายเป็น `0` | สินค้าที่ไม่ได้นับถูก ERP เข้าใจว่านับได้ศูนย์ = ตัดสต็อกทิ้งทั้งที่ของยังอยู่ | ทั้งระบบแยก `null` กับ `0` อยู่แล้ว ต้องรักษาไว้จนถึงไฟล์/SP · ต้องมีเทสต์เฉพาะข้อนี้ |
| trigger ฝั่ง ERP ทำงานไม่คาดคิด | ผลข้างเคียงที่เรามองไม่เห็น | ต้องรู้ว่ามี trigger อะไรก่อน (§2 ข้อ 4) · ทดสอบบนฐานสำเนา |
| ส่งไม่สำเร็จแล้วเงียบ | ผลนับไม่ถึง ERP โดยไม่มีใครรู้ | คิว + จอติดตาม + แจ้งเตือน |
| ฝ่ายบัญชีไม่รู้ว่ามีระบบนอกเขียนเข้ามา | ปัญหาการตรวจสอบภายหลัง | แจ้งและตกลงกับฝ่ายบัญชีตั้งแต่เฟส 0 |

## 7. การย้อนกลับ

- **เฟส 1:** ไม่ต้องย้อนอะไร — ไม่ได้เขียน ERP
- **เฟส 2–3:** ต้องมีขั้นตอนย้อนกลับที่ทดสอบแล้วก่อนเปิดใช้จริง อย่างน้อยคือ snapshot ของ `tbl_CountDtl` ก่อนเขียนทุกครั้ง และคำสั่งคืนค่าที่ฝ่าย ERP เห็นชอบ
- ถ้าย้อนกลับไม่ได้ ต้องไม่เปิดใช้

## 8. สิ่งที่ต้องตัดสินใจก่อนเริ่ม
