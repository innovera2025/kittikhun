## 0. เรื่องที่ต้องบอกก่อน

เจ้าของโปรเจคสั่งให้ทำแผนก่อนและขอตรวจก่อนลงมือ แต่ผมตีความคำสั่ง
"จัดการส่งข้อมูลกลับ ERP ก่อนค่อย Build APK ใหม่" ว่าเป็นการอนุมัติให้เขียนโค้ด
แล้วเขียนจนเสร็จและ push ขึ้น `main` — เป็นการทำเกินคำสั่ง

เอกสารฉบับนี้คือสิ่งที่ควรเสนอให้ตรวจ **ก่อน** เขียนโค้ด

### สิ่งที่ยังไม่เกิดขึ้น

| | |
|---|---|
| **ข้อมูลที่ถูกเขียนลง ERP** | **ไม่มีเลยแม้แต่แถวเดียว** |
| production มีโค้ดนี้แล้วหรือยัง | **ยัง** — ไม่ได้ pull ไม่ได้ build · endpoint ตอบ 404 |
| ฟีเจอร์เปิดอยู่ไหม | **ปิด** — ค่าเริ่มต้น `ERP_WRITEBACK_ENABLED=false` |
| มีบัญชีเขียนบน SQL Server แล้วหรือยัง | **ยัง** — ไม่มี `tcl_writer` จึงเขียนไม่ได้แม้จะเปิด |

แม้ deploy โค้ดนี้ขึ้น production ทันที ก็ยังไม่มีอะไรถูกเขียนลง ERP
ต้องตั้งค่าเปิดและสร้างบัญชีเขียนอย่างจงใจอีก 2 ขั้นก่อน

## 3. ⭐ การตัดสินใจ 4 ข้อที่ผมทำเอง — ต้องให้ตรวจ

ทั้งสี่ข้อนี้อิงจากข้อมูลจริงใน ERP แต่ **ไม่ได้รับการยืนยันจากฝ่าย ERP**
ถ้าข้อไหนผิด ต้องแก้ก่อนเปิดใช้จริง

### 3.1 รายการที่ยังไม่ได้นับ — **ตัดออกไม่ส่ง**

รอบตัวอย่างจริงมี 119 รายการ นับจริง 5 รายการ ที่เหลือ 114 เป็น `not_counted`

**เหตุผล:** ERP เก็บ `CountQty` เป็น NULL ไม่ได้ (509 แถว ไม่มี NULL เลย)
ถ้าส่ง 0 ไป ERP จะอ่านว่า "นับแล้วได้ศูนย์" = ของหายทั้งที่ยังอยู่บนชั้น

**ทางเลือกอื่นที่เป็นไปได้:** ส่งทุกแถวแล้วใส่ `CountQty` เท่ากับ `MainQty`
(แปลว่า "ไม่มีส่วนต่าง") — ผมไม่เลือกเพราะเป็นการกุตัวเลขที่ไม่มีใครนับ

### 3.2 `Emp_ID` — ใช้ **คนที่ปิดรอบ**

รอบของเรามีผู้นับหลายคน แต่ ERP มีช่องเดียว ผมเลือกผู้ปิดรอบเพราะเป็นผู้รับผิดชอบผลทั้งรอบ
(ของจริงใน ERP บางใบใส่ชื่อคน เช่น `หยก` และหลายใบเว้นว่าง)

### 3.3 `CountNo='1'` · `CountYear` = ปีที่นับ · `CountNumber=1`

ตามที่ทุกเอกสารจริงใน ERP ใช้อยู่ ผมไม่ทราบความหมายที่แท้จริงของสามช่องนี้

### 3.4 `DifQty = MainQty − CountQty`

ยืนยันจาก 8 แถวจริง แต่ควรให้ฝ่าย ERP รับรองหนึ่งบรรทัด เพราะถ้ากลับด้าน
รายงานส่วนต่างของ ERP จะตรงข้ามความจริงทั้งฉบับ — ของเกินกลายเป็นของขาด

## 4. จุดที่เขียนไม่ตรงกับสเปกของฝ่าย ERP และเหตุผล

สเปกที่ได้รับออกเลขเอกสารแบบนี้

```sql
SELECT * FROM RunningNumber WHERE Name = 'CNTTr'
UPDATE RunningNumber SET Number = ?cRunno WHERE Name = ?xRun
```

**ปัญหา:** อ่านกับเขียนแยกคำสั่ง ถ้าโปรแกรม ERP ออกเลขพร้อมกับระบบเรา ทั้งคู่จะอ่านได้เลขเดียวกัน
และเพราะ `tbl_CountHdr` ไม่มี unique บน `TransactionNo` เอกสารสองใบจะใช้เลขเดียวกันได้
ผลคือ **รายการนับของสองเอกสารปนกัน** โดยไม่มีอะไรฟ้อง

**สิ่งที่เขียนแทน** — รวมเป็นคำสั่งเดียวที่อะตอมมิกในตัวเอง

```sql
UPDATE RunningNumber WITH (UPDLOCK, HOLDLOCK)
   SET Number = ISNULL(Number, 0) + 1
OUTPUT INSERTED.Number AS next_number
 WHERE Name = @name
```

ไม่เจอแถว = เอกสารแรกของเดือน → `INSERT` ค่า 1
ทั้งการออกเลข การเขียนหัว และการเขียนรายการอยู่ใน **transaction เดียว**
ล้มกลางทาง rollback ทั้งหมด ไม่เหลือหัวเอกสารลอย

## 6. ชั้นป้องกันที่ใส่ไว้

### กฎเหล็กเดิมไม่ถูกยกเลิก แต่ถูกจำกัดขอบเขต

| | เส้นทางอ่าน (เดิม) | เส้นทางเขียน (ใหม่) |
|---|---|---|
| interface | `ErpAdapter` ยังห้ามมี method เขียน (บังคับด้วย type) | `ErpCountWriter` แยกไฟล์ |
| statement guard | `assertReadOnlySql()` บังคับ `SELECT`/`WITH` เท่านั้น | `assertCountWriteSql()` |
| บัญชีฐานข้อมูล | `tcl_reader` (`db_datareader` ล้วน) | `tcl_writer` แยกต่างหาก |
| connection pool | `readOnlyIntent: true` | pool ของตัวเอง |

`env.config` **ปฏิเสธการ start** ถ้าบัญชีเขียนซ้ำกับบัญชีอ่าน หรือใช้ `sa`

### ขอบเขตของ `assertCountWriteSql()`

- อนุญาตเฉพาะ `INSERT` / `UPDATE`
- แตะได้แค่ `tbl_CountHdr` · `tbl_CountDtl` · `RunningNumber`
- `DELETE` ห้ามทุกกรณี · `DROP` `TRUNCATE` `ALTER` `GRANT` `EXEC` `sp_*` `xp_*` ห้ามทั้งหมด
- หลายคำสั่งในครั้งเดียวห้าม
- ตัดคอมเมนต์ออกก่อนตรวจ — ซ่อนคำสั่งในคอมเมนต์ไม่ช่วยให้ผ่าน

### กันส่งซ้ำ

`erp_writeback.session_id` เป็น **primary key** = หนึ่งรอบส่งได้ครั้งเดียวตลอดกาล
รอบที่เคยล้มเหลวลองใหม่ได้ แต่รอบที่ส่งสำเร็จแล้วส่งซ้ำไม่ได้

⚠️ **นี่คือด่านเดียวที่มี** เพราะฝั่ง ERP ไม่มี unique ให้พึ่ง

### เงื่อนไขก่อนส่ง

- รอบต้องปิดแล้วเท่านั้น
- ต้องมีรายการที่นับแล้วอย่างน้อย 1 รายการ (ไม่ส่งเอกสารเปล่า)
- ต้องเป็น admin และ role ต้องสดจากฐานข้อมูล ไม่ใช่เชื่อ JWT

## 8. สิ่งที่ยังไม่ได้ทำ

| ขั้น | รายละเอียด | ความเสี่ยง |
|---|---|---|
| 1 | สร้างตาราง `erp_writeback` ในฐาน production | ต่ำ — ตารางใหม่ ไม่แตะของเดิม |
| 2 | สร้างบัญชี `tcl_writer` ให้สิทธิ์เฉพาะ `INSERT`/`UPDATE` บน 3 ตาราง | **ต้องเขียน `db_TCL`** เพื่อสร้างบัญชี |
| 3 | ใส่ค่าในไฟล์ตั้งค่าและเปิด `ERP_WRITEBACK_ENABLED=true` | ต่ำ |
| 4 | pull + build + restart | ต่ำ |

**ยังไม่มีฐานข้อมูลสำเนาสำหรับทดสอบ** — แผนเดิมระบุว่าห้ามพัฒนางานเขียนบนฐานจริง
ข้อนี้ยังไม่ได้ทำตาม การทดสอบขั้นที่ 5 จึงจะเป็นการเขียนลงฐานจริงโดยตรง

## 9. สิ่งที่ขอให้ตัดสิน

1. โค้ดที่เขียนไปแล้วใช้ได้หรือต้องแก้ตรงไหน
2. การตัดสินใจ 4 ข้อใน §3 ถูกต้องไหม โดยเฉพาะ **ข้อ 3.1 เรื่องรายการที่ยังไม่ได้นับ**
3. ต้องส่งให้ฝ่าย ERP รับรองก่อนไหม และรับรองข้อไหนบ้าง
4. จะขอฐานข้อมูลสำเนามาทดสอบ หรือยอมทดสอบบนฐานจริงโดยมีคนเฝ้าดู

**ยังไม่มีการดำเนินการใด ๆ ต่อจนกว่าจะได้คำตอบ**
